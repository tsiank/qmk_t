# nRF52840 三模与 ESB 接收器

ciank67 使用 USB / BLE / 2.4G 三模；ciank_pad 仅借用硬件作为专用 USB 接收器。保留 SDK 15、
S140 6.1.1、现有 Bootloader，公共实现位于 `platforms/nrf5/esb_*`。

当前使用 R13：`ciank67-default-esb-r13.zip`（键盘）、`ciank_pad-esb-rx-r13.zip`
（接收器）和 `app-esb-r13` 客户端。两端都需要更新；保留原配对，不需要重新配对。
R13 经接收器支持 VIA、宏、键盘控制、校时/屏幕（键盘有此能力时）、律动和双向
USB MIDI。客户端选择“2.4G 接收器”，键盘本体用电池供电并选择 2.4G/自动模式，
接收器仍插电脑 USB。MIDI 页选择名为 Qmknrf5 2.4G Receiver 的 MIDI 输入。
目前已通过模拟和构建检查，R13 的完整实机转发链路仍需刷入后验证。

R12 恢复了正常 default 键位，R13 沿用。用户已确认
R11 分块写入后灯光开关和 Caps 指示正常。`default` 原有键位及层编号：
Dvorak 基础层、符号、数字、Fn、QWERTY、灯光、鼠标依次为 0–6；不强制切换
到临时 QWERTY。正常 VIA 编辑/保存恢复，不再每次启动清空键位或拦截编辑。
从 R7–R11 测试镜像首次刷入时，利用其留下的无效 VIA 标记初始化正常键位，
后续启动保留 VIA 修改；蓝牙绑定、接收器配对、输出偏好和灯光配置保留。
`make ciank67:default` 直接编译三模，`esb_tx` 作为相同键位的兼容目标。
下文 R7–R11 的固定键位说明是测试历史，已被 R12 替代。

R1 的实板测试已确认连接、输入、组合键、Caps Lock 和其他反馈项目通过；因没有
电池开关，断电释放尚未实测。R2 加入 USB 配对、加密握手、配对保存与三模切换。R3 改为键盘与接收器无线配对，
已做本地协议/加密/双实例模拟测试，新的配对流程仍需两块板子的实际验证。

R4 修正 R3 专用接收端的启动顺序：SDK 15 的 `nrf_drv_power_init` 必须在
SoftDevice 启用前调用。否则 USB 初始化报 `NRF_ERROR_INVALID_STATE`，接收端
不会正常枚举，发送端最终配对超时。请使用 R4 接收端固件替换 R3。

R5 修正自动模式的在线判断：键盘自身 USB 优先，其次是通过认证探测到的 2.4G
接收器，接收器断开后启动蓝牙重连。处于蓝牙时，以约 500 个计时单位的间隔发起
HELLO 探测，每次最多 3 次、间隔约 40 个计时单位的重试；不携带键盘、鼠标或
媒体键报告。接收器恢复后自动切回 2.4G，切换前清除旧主机按键。已选自动模式时，
重新配对会保留自动偏好。手动 USB／蓝牙／2.4G 模式仍保持所选输出。

与 R4 接收器协议兼容；本次只需更新键盘为 `ciank67-esb-tx-r5.zip`，
不需要重新配对，原有蓝牙绑定与 2.4G 配对均保留。

R6 修正蓝牙重新配对入口：`ADVW` 从任意输出模式请求切到蓝牙，等待路由切换及
原 GAP 连接断开后，再开放无白名单发现。Windows 已删除配对、键盘仍留有旧记录时，
仅在这个显式配对操作期间允许更新该绑定；正常重连仍拒绝无授权的重新配对。
成功加密、退出蓝牙模式或广播超时后关闭此许可，不自动删除全部蓝牙绑定。

当前推荐：发送键盘 `ciank67-esb-tx-r6.zip`，接收器继续使用 R4，无需更新接收器。

默认映射：`Fn + Q` 为固定 USB（`OU_USB`），`Fn + W` 为固定蓝牙（`OU_BT`），
`Fn + R` 为固定 2.4G（`OU_2P4G`），`Fn + 3` 恢复自动（`OU_AUTO`）。
固定模式不会因插 USB 而被覆盖。因此 `OU_USB` 后可以打字表明 USB 路径正常，
若希望插拔自动切换应选 `OU_AUTO`。

在 Windows 删除旧蓝牙配对后：按 `Fn + ↑`（`ADVW`）进入可发现的蓝牙配对，
在 Windows 添加设备；成功后按 `Fn + 3` 恢复自动。已有 VIA 映射可能不同，应以
实际键码为准。旧 R5 可以先 `OU_BT`、再 `ADVW`；R6 已合并为一个显式配对动作。

R7 为用户要求的临时固定键位测试版：每次启动重置 ciank67 的 VIA 键位、宏与
布局选项，暂停 VIA 改键，实际输入始终读取固件内置键位。蓝牙绑定、2.4G 配对和
输出偏好不清除。私有 USB／蓝牙控制接口保留用于输出模式、律动等配置。测试镜像
的 VIA 有效标记保持无效，后续恢复普通 VIA 固件时会初始化自己的布局。

本版以 QWERTY 启动。两种基础布局中，Fn 统一在底排从左数第 7 颗，数字层在
第 6 颗。基础层低于功能层，Fn 设为最高优先级，避免原先 QWERTY 层覆盖 Fn。
Fn／数字层的 `3`、`Q`、`W`、`R` 分别为 `OU_AUTO`、`OU_USB`、`OU_BT`、
`OU_2P4G`；`Fn + ↑` 为 `ADVW`。旧 VIA 映射不参与本版的按键解析。

当前请用 `ciank67-esb-tx-r7.zip` 更新键盘，接收器继续使用 R4。待三模功能验证
完成，再恢复 VIA；本版不保留旧 VIA 自定义键位或宏。

R8 是 Caps Lock 回传诊断包，尚未认定无线指示灯问题已经修复。保留 R7 固定键位
和现有无线协议，只增加状态观测。键盘、接收器都使用 R8 才能读取两端的 LED 状态。

`0x83` 诊断版本变为 2，原 0–28 字节布局不变。29–31 字节：

- 键盘：29 的低 5 位为当前输出主机的 LED 位，bit 7 为 Caps 底灯层是否启用；
  30 为最近一份蓝牙 LED 写入的原始字节，31 为蓝牙 LED 写入次数（模 256）。
- 接收器：29 为 USB LED 状态，30 为最近输出报告缓冲的首字节，31 为输出写入
  次数（模 256）。计数用来区分没有收到主机写入和收到的状态确实为零。

Windows 只读脚本 `D:\kbdmusic\read-caps-state.ps1` 同时查询两端 USB 私有接口。
需要键盘本体也临时接 USB，并用 `Fn + W` 明确选择蓝牙（或 `Fn + R` 选择无线），
避免自动模式因 USB 供电切回有线。打开 Caps Lock 后运行脚本，日志保存在
`D:\kbdmusic\caps-state-log.json`。脚本不改变输出模式、配对、键位或灯光设置。

R9 针对底灯关闭时静态指示的首帧可靠性作修正。R8 实机蓝牙记录已确认：
主机 LED 字节为 `2`、蓝牙原始报告为 `2`、Caps 底灯层已开启，但白灯未显示；
用户反馈多按几次后会亮，手动蓝牙模式接 USB 供电仍可复现。
这说明至少蓝牙这一路的状态已经到达指示层，不能归因于没有主机回传。

本版在 nRF 底灯电源实际从关闭转为开启时等待 2ms 再发首帧；静态指示层变更后，
以 20ms 间隔额外刷新两次当前合成画面，然后停止重试。重试不保存旧帧、不打开
底灯总开关，也不写灯光配置；已供电动画不额外等待。只需给键盘刷入
`ciank67-esb-tx-r9.zip`，接收器保留 R8、配对保留。原始蓝牙报告诊断仍可读取。
自动化测试验证上电等待、有限重试及关闭后不恢复旧白灯；USB／蓝牙／2.4G
首次按 Caps 的实际显示效果仍需实机确认，尚未认定彻底修复。

R9 用户已确认 Caps 指示恢复正常；随后报告电池供电的 BLE／2.4G 下灯光开关
不稳定，退出客户端仍可复现，固定 BLE 接 USB 供电则正常。用户同时看到 BLE
设备断连，采样也遇到 GATT 响应中断；当前不能把断连直接认定为 MCU 重启或
电池故障。R10 保留 R9 灯光逻辑，增加只读诊断，不作为该新问题已修复的声明。

R10 发送端新增 `0x82`（复用已有 UI 故障包）和 `0x85`（灯光观测包）。SDK
致命错误记录保留于 NOLOAD RAM，软件复位后可读取；掉电后不保证保留。
`0x82` 原布局不变：版本 1，2–5 运行毫秒，6–9 fault ID、10–13 PC、14–17
info、18–21 SDK error code、22–25 FDS 首地址、26–29 bootloader 地址、30–31
RESETREAS。无记录时故障字段为零；RESETREAS 可包含早先复位原因，不单独据此
认定本次重启，结合运行时间回退判断。

`0x85` 32 字节，多字节大端：1 版本（1）；2 Matrix/Underglow 开关位（bit0/1）；
3 底灯电源 GPIO 输出值（ciank67 为 0 开、1 关）；4–7 运行毫秒；8–9 ADC
估算电池毫伏（0 表示尚未测得）；10–11 灯光开关键按下次数、12–13 松开次数；
14–15 客户端非零掩码控制次数；16–17 最近灯光开关键码；18 最近按键边沿；
19 最近客户端掩码；20/21 Matrix 模式/亮度；22/23 Underglow 模式/亮度；
24 最近客户端值；25–31 保留零。关闭时 Underglow 模式 getter 返回 0。
计数为 16 位、重启清零，查询不增加控制次数，不改变开关或写 Flash。

R10 只刷键盘 `ciank67-esb-tx-r10.zip`，接收器继续 R8，不重新配对。
蓝牙只读采样工具位于 `D:\kbdmusic\caps-ble-probe`，查询两类诊断并在超时后
尝试重新连接，以保留重连前后的运行时间、开关和故障信息。

R10 实机已抓到多次复位：灯光按键后的运行时间从约 47 秒回到约 1 秒，
按键计数清零，客户端控制写入次数始终为零。一次矩阵灯操作后约 0.5 秒即
断连，符合 EEPROM 的延迟保存时间。未捕获到 SDK fault 记录；不能据此排除
软件故障，因为记录经过 Bootloader 后的 RAM 保留仍依赖 Bootloader 布局。

R11 将 ciank67 VIA 配置的 `NRF_FSTORAGE_SD_MAX_WRITE_SIZE` 从 SDK 默认
4096 字节限制为 128 字节，与 ciank_pad 相同。2 KiB EEPROM 的异步 FDS
快照、保存/GC 重试和配对区均保持原逻辑；不通过禁用持久化绕过问题。
编译预处理已确认 SDK 看见 128，仍需实机确认该改动能否消除复位。
只刷键盘 `ciank67-esb-tx-r11.zip`，接收器保留 R8，R10 诊断接口保持可用。

R10 同时读到普通底灯亮度为 0，而 Caps 白灯使用独立亮度。开关开启且普通
底灯不亮时，先提高 `UG_VALU`，避免把零亮度误判为开关失效；不自动覆盖用户的
HSV 配置。本测试映射 `Fn+↓` 进入灯光层，松开后按 QWERTY 的 G 位置为
`UG_VALU`，H 为 `UG_VALD`。

## 无线配对与提示（R4 及以后）

1. 分别给 ciank67 刷入 `ciank67-esb-tx-r8.zip`，给 ciank_pad 刷入
   `ciank_pad-esb-rx-r8.zip`。只更新应用，两端需支持 R3 无线配对。
2. 把 ciank_pad 接收器插入电脑 USB；ciank67 可直接使用电池，不需要接 USB。
3. 插入后约 60 秒内，ciank67 同时长按物理左右 Ctrl 约 3 秒；也可长按已配置的
   `OU_2P4G` 键约 3 秒。左右 Ctrl 物理组合独立于 VIA，旧映射也可使用。
4. 双方自动交换、校验并保存密钥，键盘自动切到 2.4G（原为自动模式时保留自动选择），即可输入。**全程不需要
   客户端、接收器按键或屏幕，也没有客户端确认步骤。**

已有绑定会自动重连。每次接收器插入 USB 并完成枚举，开放约 60 秒的发现窗口，同时仍接受
原绑定键盘的正常输入；只有收到新的键盘配对请求才切换到交换流程。窗口关闭后
不会自动接受陌生键盘。超过时间需要配对时，重新插拔接收器，再操作键盘配对键。
配对成功立即关闭本次发现窗口，保留约 20 秒完成应答重试管道（不接受其他候选）。

客户端是可选的管理工具：查看状态、重新开启窗口、取消配对、清除绑定及进入 DFU。
日常输入和首次配对均不依赖客户端进程。

R4 键盘底灯提示（不写入灯光配置，底灯关闭时也能显示，结束恢复原状态）：

| 提示 | 含义 |
| --- | --- |
| 蓝色慢闪 | 正在寻找接收器 |
| 黄色快闪 | 已发现接收器，交换密钥／保存中，或等待加密输入连接 |
| 绿色闪三次 | 双方配对已保存，键盘已建立经过认证的无线连接 |
| 红色闪三次 | 配对失败、超时，或保存后仍未建立无线连接 |
| 橙色闪三次 | 已取消配对 |

默认 Fn 层和数字层的第二行第五键（QWERTY 的 R 位置）是 `OU_2P4G`：
短按切到 2.4G，长按约 3 秒进入配对。第一行第四键是 `OU_AUTO`。
旧 VIA 自定义映射保留，不会自动添加这些键；可在 VIA 搜索并设为 `OU_2P4G`。

接收器不扫描实体按键或旋钮，不启用本地 OLED、RGB、QMK 布局或 BLE HID。
VIA 和音乐控制由无线代理转给键盘；USB MIDI 使用独立接口。没有本地键盘布局或
按键配对操作。进入刷机模式：查找并选择接收器后，点击
“接收器进入固件刷入模式”，再到固件刷入页面选择 ZIP 与 DFU 串口。
首次由普通 pad 固件切换时，仍使用原固件的 DFU 入口。

双方密钥校验完成并进入保存前，取消或超时不会覆盖旧绑定。键盘可按 Esc 或切换输出模式取消；
接收器可用客户端取消。进入 Flash 保存时不允许取消。发送端锁定候选后
允许额外时间完成对端保存，避免窗口末尾开始保存时发生一端刚保存、另一端先超时。
若保存期间断电或长时间断链导致两端不一致，重新开启无线配对即可恢复。

已有 R2 配对记录仍可用于普通加密输入；首次使用新的无线配对流程需要两端 R3。
旧的双 USB 写入接口保留作恢复 API，不再是客户端的主要配对流程。

## 输出模式

| 选择 | 行为 |
| --- | --- |
| 自动 `OU_AUTO` | 键盘自身 USB 优先，否则选择实际在线的已配对 2.4G；接收器不在线则蓝牙，恢复后自动切回 |
| USB `OU_USB` | 只向 USB 主机输出，未接 USB 时不自动换其他主机 |
| 蓝牙 `OU_BT` | 只向蓝牙主机输出，USB 可继续用于供电和本板配置 |
| 2.4G `OU_2P4G` | 只向已配对接收器输出，USB 可继续用于供电和本板配置 |
| 关闭输出 `OU_NONE` | 不向主机提交按键，仍可由本板 USB 配置恢复 |

选择会保存到键盘。USB 插拔、蓝牙连接事件不会覆盖手动选择；只有自动模式会
随 USB 和接收器在线状态选择主机。蓝牙仍使用原来的 Windows 蓝牙配对与键盘蓝牙配对键。

ciank67 的 Fn / 数字层中，原有 USB / 蓝牙键保留；第二行第五个位置增加
`OU_2P4G`，第一行第四个位置增加 `OU_AUTO`。若沿用了已有 VIA 键位，固件
不会覆盖自定义布局，请在客户端 VIA 键位选择器中添加这两个键码。

切换先清除旧主机按键，2.4G 的释放队列最多等待 100ms；若链路已经断开，接收器
约 300ms 超时释放。过渡期间保持本板 VIA 回复可用，避免改键连接因切换而失效。

接收端由 `platforms/nrf5/dongle/` 的独立主程序和 USB 服务驱动，构建时排除 QMK
键盘代码及 BLE 服务。它保留 S140 SoC 的时隙、随机数和 Flash 服务，未启用 BLE
协议栈。USB 转发键盘、NKRO、媒体键和鼠标报告，Caps Lock 等 LED 状态回传键盘。
`ciank_pad:esb_rx` 仅为当前验证板的构建目标；普通 pad 固件不受影响。
以后使用真实 nRF52840 接收器时，复用通用接收端代码，另配其时钟、USB 标识和
Bootloader 参数；不需要移植 pad 的屏幕、按键或 VIA 功能。

## 编译

```sh
make ciank67:default
make ciank_pad:esb_rx
```

编译不自动刷机。应用 DFU 包参数与原固件相同：
`--hw-version 52 --application-version 1 --sd-req 0xB6`。
`ciank67:default` 现在启用 ESB 发送功能；`ciank_pad:test` / `default` 仍不启用
ESB，刷回 pad 普通应用即可退出接收角色。独立配对记录保留。

## 实现与验证

- `esb_settings.c`：独立 FDS 文件 `0x1002` / 记录 `0x1001`，32 字节、版本标识及
  CRC，保存密钥、随机无线地址和输出偏好。Flash 写入使用持久快照，不覆盖 VIA EEPROM。
- `esb_pair.c` / `esb_pair_crypto.c`：限时窗口、X25519 临时公钥交换、HKDF-SHA256
  派生独立链路密钥和确认密钥、HMAC 密钥确认、USB 插入窗口授权、两端自动分步保存。
  使用 SDK 自带 Oberon 库，在主循环运行，不传输私钥或链路密钥。
- `esb_packet.c`：普通输入继续使用 R2 帧，16 字节公开头（版本、类型、长度、64 位启动随机数、
  32 位计数器），最多 32 字节报告及 8 字节认证标签。
- `esb_crypto.c`：RFC 3610 AES-CCM 加密/校验数据，RFC 4493 AES-CMAC 校验确认包。
  数据密钥由两端会话随机数派生，与 HELLO / ACK 使用的密钥分离。
- `esb_transport.c`：HELLO / 新鲜挑战握手、RTC 回绕扩展、严格有序数据、重复包过滤、定期状态
  刷新、断线释放和队列积压恢复。计数器即将用尽时更换启动随机数，不复用数据 nonce。
- `esb_radio.c`：ESB 扩展动态长度、2Mbps、16 位 CRC，运行于 S140 Timeslot。
  只在授权时操作 RADIO / TIMER0。配对期间使用公共发现地址；接收器保存后额外
  保留约 20 秒发现管道，配对完成应答丢失时仍可重试，同时开始接受私有地址的输入。
  软件应答按接收管道选择返回地址。收到包后先在主循环完成认证，再缓存完整包及
  已签名的 ACK；下一次重传命中缓存时才在无线中断快速应答。
- `dongle/usb.c`：独立接收器 HID 服务，专用 USB 缓冲完成前不复用；BUSY 重试、不在无线回调调用 USB。
- `outputselect.c`：持久手动偏好、自动选择、释放旧主机与延后切换。

AES 使用 S140 的 ECB API，全部在主循环；无线回调不调用 SVC、Flash、USB、QMK
或 I²C。每次时隙最多 8ms，在结束前 200µs 归还资源，成功发送可提前结束。

接收器启动或发送端更换启动随机数时建立新挑战；旧会话的录包不能作为新输入。
重复包可以获得确认，但不会再次输入或延长按键超时。ACK 校验覆盖完整计数器、
挑战、接收状态与 Caps Lock 等 LED 状态。无线确认并不等于 Windows 已消费输入。
极端积压 / 断线恢复允许丢弃旧的短促点按，以避免卡键。

当前仍使用固定信道 40（2440MHz），没有跳频；2.4G 模式与接收角色暂不自动
System OFF，功耗和干扰性能需实测。无线配对采用插入窗口的 Just Works 方式，没有预共享设备身份或可在两端比较的
显示码；能保护密钥不被被动窃听，但不提供主动中间人攻击的身份认证。只在自己准备配对时插入接收器并操作键盘配对键；此项目自定义协议未经过独立安全审计。

R13 同时保留键盘本体 USB／蓝牙接口，并增加接收器代理。接收器的管理 HID
（`FF67:0068`）继续本地处理 `0x83` / `0x84`；其余 VIA 命令无线转发，回复仍为
32 字节。`C7` 开头的 20 字节音乐/控制包补零到 32 字节，通过同一 HID 代理；
普通音乐帧/颜色写入无 USB 回复，控制请求返回补零的原 20 字节状态包。
客户端通过同一连接池串行访问 VIA、控制、律动和接收器管理，防止多个读取者争抢回复。

无线层保留原 30 字节认证 ACK。需要下行时扩展为 64 字节，后 34 字节为
序号（4，大端）、种类（1）、长度（1）、密文（最多 20）、零填充及 CCM 标签（8）。
CCM 头按原发送会话和下行序号重建，使用独立 `Qmknrf5 DOWN v1` 派生域及方向
nonce `1`；会话与接收器挑战共同派生密钥，避免与上行复用密钥/nonce。
VIA 下行分为两个 16 字节片段，附带请求 token；上行最多 24 字节片段，附带
token、片段/末片标志及下行确认号。控制和 MIDI 使用可靠队列，只有接收端应用
队列接受后才确认；重复无线帧不会再次执行。律动帧仅保留最新待发帧，避免堆积。
HID 与服务交替调度，未确认数据保持不可变。断线/USB 重置建立新会话并清理请求、
停止律动与 MIDI；接收器向主机发送全通道 All Sound Off，避免丢失 Note Off 后长鸣。

接收器新增 USB AudioControl/MIDIStreaming 接口 5/6，使用独立 EP6 IN/OUT。
键盘 MIDI 可发送到电脑合成器，电脑 MIDI 输出也可转到键盘原有 MIDI 输入处理。
接收器不运行本地 QMK 音乐或蜂鸣器。音乐与 MIDI 共用无线带宽，射频干扰下的
实时表现仍需硬件测试；此版本仍使用固定信道，没有跳频。

## 测试与诊断

```sh
python3 -m unittest discover -s platforms/nrf5/tests -v
```

加密测试将真实 C 实现与 Python cryptography 的独立 CCM / CMAC 结果对照；
双实例模拟执行真实发送 / 接收代码，覆盖握手、录包重放、接收端重启与错误密钥。
这些不替代两块板子的实际射频时序、Flash 保存和模式切换测试。

接收器管理 HID（Usage Page `0xFF67` / Usage `0x0068`，32 字节、无 Report ID）支持
`0x83` 诊断。发送端仍通过自身 VIA Raw HID 访问相同命令。诊断（32 字节，多字节数大端）：1 版本；2 角色；3 连接状态；
4–7 时隙错误；8–11 时隙数；12–15 发送次数；16–19 ACK 次数；20–23 接收次数；
24–27 拒绝 / 取消时隙数；28 报告队列长度。

`0x84` 配置请求：1 操作（0 查询、1 模式、2 USB 恢复配对、3 清除、4 开启无线窗口、
5 确认候选（旧手动流程兼容）、6 取消、7 接收器应用 DFU），2 请求版本 1，
3 模式（仅操作 1）；操作 2 的 4–19 为密钥、20–23 为无线地址；30–31 请求序号。
操作 7 仅由专用接收器接口提供，配对／保存时拒绝；发送响应完成并延迟 200ms 后重启。
其余保留字节为零。回复：1 版本、2 错误、3 角色、4 偏好、5 当前模式、6 已配对、
7 保存状态（0 正在保存 / 1 完成 / 2 错误）、8 无线连接、9–12 地址、13–20 芯片 ID、
21–24 保存错误、25–26 请求序号、27 配对状态、28 窗口剩余秒数、29–31 候选标识。
配对状态：0 空闲、1 等待、2 已发现、3 待确认、4 保存中、5 已保存、6 失败、7 超时、
8 取消。候选标识用于操作辨识，不是用于认证的口令。回复不包含密钥。
